# Smart Sender — Webhooks (тестове завдання)

Вхід, список вебхуків із пагінацією/пошуком і редагування. API повністю імітується через MSW.

**Стек:** React 19, TypeScript (strict + `noUncheckedIndexedAccess`), Vite, React Router 7, TanStack Query 5, MSW 2, Vitest.

## Запуск

```bash
npm install
npm run dev        # http://localhost:5173
npm test           # автотест сесії
npm run typecheck
npm run build      # tsc + vite build (MSW увімкнений і в збірці, бекенду немає)
```

## Структура

```
src/
  api/          API-шар без React: транспорт, CSRF, ротація сесії, типи контракту
    http.ts            fetch + заголовки + CSRF (+ повтор на 419) + розбір помилок
    session-guard.ts   401 → спільний rotate → один повтор
    api.ts             ендпоінти контракту (createApi)
  auth/         стан сесії (external store) і дії login / logout / restoreSession
  app/          синглтони (api, queryClient, sessionStore), роутер, layout
  features/     login, webhooks (сторінки, запити TanStack Query, URL-параметри)
  mocks/        MSW: in-memory БД і хендлери за контрактом
```

API-шар не залежить від React, тому тестується напряму в Node через `msw/node`.

## Ключові рішення

### Сесія і повтори (`src/api/session-guard.ts`)

- Захищені ендпоінти йдуть через guard, auth-ендпоінти (`login`, `issue`, `rotate`, `revoke`) — напряму через транспорт.
  Тому rotate фізично не може запустити інший rotate.
- На 401 запит чекає **один спільний** promise rotate і повторюється рівно один раз.
- Лічильник `generation` збільшується після кожного успішного rotate. Якщо запит був відправлений до rotate,
  а його 401 прийшов уже після завершення rotate, він просто повторюється без нового rotate — інакше «запізнілі» 401 давали б зайві ротації.
- Нові запити, що стартують під час rotate, спочатку чекають на нього.
- Помилка rotate або 401 на повторі → `onSessionExpired`: очищення кешу TanStack Query, стан `anonymous`, редирект на вхід
  з поверненням на ту ж URL (разом із параметрами списку) після повторного входу.
- `device_session_token` існує лише як локальна змінна у `login()` між `/auth/login` і `/auth/token/issue`.
- `fingerprint` — 16 випадкових байтів з `crypto.getRandomValues` (32 hex), зберігається в `localStorage`.
- Токени сесії клієнт не бачить: сесію тримає мок (аналог HttpOnly-cookie). При старті застосунок пробує
  `/v1/me` — з реальною cookie сесія відновилася б; у моку стан у пам'яті скидається при перезавантаженні, тож буде екран входу.
- Вихід: `revoke` (результат не важливий) → очищення кешу й локального стану.

### CSRF (`src/api/http.ts`)

- Усі запити мають `X-Requested-With: XMLHttpRequest`.
- Перед першим запитом виконується `GET /csrf` (паралельні запити ділять один виклик), токен іде в `X-CSRF-TOKEN` на POST/PUT.
- На 419 токен отримується заново і запит повторюється не більше одного разу.
- Капча: мок приймає будь-яке непорожнє значення `X-Captcha-Token`, клієнт надсилає заглушку (`CAPTCHA_TOKEN_STUB` в `api.ts`).

### Список

- Сторінка й пошук живуть тільки в URL (`?page=2&search=order`) — перезавантаження й «назад»/«вперед» працюють без додаткової синхронізації.
  Значення за замовчуванням з URL прибираються.
- Пошук із debounce 300 мс; зміна пошуку скидає сторінку на першу.
- `keepPreviousData` — при перемиканні сторінки старі дані лишаються на екрані (притемнені), без мерехтіння.
- Стани: завантаження, помилка з кнопкою повтору, порожній результат (окремо для пошуку і для сторінки за межами діапазону).

### Редагування

- Окрема сторінка `/webhooks/:id` — посилання можна відкрити напряму; «назад» повертає на ту ж сторінку списку з тим же пошуком.
- Валідація лише серверна: 422 `payload` відображається біля відповідних полів; помилки полів, яких немає у формі, показуються як загальна помилка форми.
  Помилка поля зникає, коли користувач його змінює.
- Після збереження оновлюється кеш деталі та інвалідуються всі сторінки списку.

### Мок (`src/mocks`)

- 27 вебхуків, один користувач, стан лише в пам'яті. Хендлери створюються фабрикою `createHandlers({ baseUrl, db })`,
  тож тест отримує свіжу БД і прямий доступ до неї (наприклад, щоб «прострочити» сесію без очікування 30 с).
- CSRF перевіряється до виконання операції; сесія — 30 с, rotate продовжує на 30 с; до `issue` і після `revoke` rotate → 400.
- Помилки — у форматі контракту (`{ error: { type, message, payload? } }`).

## Тест

`src/api/session-guard.test.ts` (`npm test`):

1. **Основний за завданням:** сесія прострочена → `GET /v1/me` і `GET /v1/webhooks` паралельно отримують 401 → рівно один `rotate` → обидва повтори успішні.
2. Rotate повертає 400 → обидва запити завершуються `SessionExpiredError`, викликається `onSessionExpired`.
3. 419 → повторний `GET /csrf` → один повтор `PUT`.

Додатково `src/app/app.test.tsx` — інтеграційні UI-тести (jsdom + Testing Library + той самий MSW-мок), що проходять
сценарії завдання через інтерфейс: вхід і помилка поля, URL-параметри (deep link після «перезавантаження», скидання сторінки
при пошуку, «назад»/«вперед»), порожній/помилковий стани, редагування з 422, прозорий rotate і вихід на логін при його помилці,
logout з очищенням кешу. `src/test/jsdom-environment.ts` повертає Node-шні `AbortController`/`AbortSignal`,
бо `fetch` у Node не приймає jsdom-івський `AbortSignal`.

## Що свідомо не зроблено / компроміси

- Немає e2e-тестів у реальному браузері (Playwright) — UI перевіряється в jsdom.
- Відповіді API типізовані через generic без runtime-валідації (zod тощо) — для мока, що реалізує той самий контракт, це надлишково.
- Немає клієнтської валідації форми — джерело правди сервер, а завдання перевіряє саме відображення серверних помилок.
- Кожне «завершене» (після debounce) значення пошуку додає запис в історію; для «назад»/«вперед» це очікувано, але можна перейти на `replace`.
- Без UI-бібліотеки: мінімальний власний CSS.
